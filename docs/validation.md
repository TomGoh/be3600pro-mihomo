# RN01 验证记录

日期：2026-11-09，UTC+8。对象：小米 BE3600 Pro（RN01），原厂 1.0.74，Linux 5.4.213 ARMv7。Android 实机为小米 17 Pro。

以下是单台设备上的工程验证，不等同于所有固件或场景的验收。原始日志保存在维护者电脑的忽略目录，本文不包含真实设备 MAC、订阅、节点凭据或管理令牌。

## TCP 接管切换

真实直播曾在开启代理后短暂停顿，随后恢复。同期采样中，接管期间 CPU 平均约 16.8%，最忙核心峰值约 48.6%，可用内存最低约 138 MiB，网络软中断队列没有新增丢包；电视的视频连接确实命中 DIRECT 并持续接收数据。

进一步用电脑和路由器上的双栈回显 peer 做受控对照：

| 条件 | 开启前已有 IPv4 TCP | 开启前已有 IPv6 TCP | 开启后新 IPv4/IPv6 TCP |
|---|---|---|---|
| 原先的无条件 TCP TPROXY | 切换后超时 | 切换后超时 | 正常 |
| 透明 socket + 新 SYN 接管 | 连续通过 16 秒 | 连续通过 16 秒 | 各连续通过 5 秒 |

修复为：已经对应透明 socket 的 TCP 包继续进入代理；新连接的 SYN 进入代理；其余旧的普通 TCP 包继续原路径。测试使用临时文档地址及很低的数据量，结束时恢复模式、撤掉测试接管并移除地址。

这是对一个已复现中断机制的修复。**修改后没有由观看者再次确认完整咪咕直播的长时间流畅性**，也没有证明所有直播卡顿都来自同一原因。关闭代理时，已有代理连接仍可能需要重连。

## 终端原有 Clash 并存

补充实测发现：电脑自己的上游代理连接也被路由器按 MATCH 再次代理。关闭路由器接管时，同一个电脑客户端正常；开启后该客户端 TLS 连接超时，路由器自身的联网探针仍正常。抓到的相关连接与配置中的节点地址、端口匹配。

修复为在启用时解析配置与已管理来源中的上游地址/端口，建立 IPv4/IPv6 `hash:ip,port` 集合；只让这些端点保持原生连接。实机修复后，同一电脑 Clash 客户端 HTTPS 检查恢复 HTTP 204，路由器的 DNS、双栈 HTTPS 和双栈 STUN 同时全部通过。不是对电脑整机放行；同地址的其他端口仍按正常规则处理。

## UDP 回包

固定 Mihomo 上游 v1.19.32 对应提交，并提供完整源码补丁。针对透明 UDP 回包源端口被占用时的 EADDRINUSE 分支增加 RAW 回包路径；IPv4 使用 IP_TRANSPARENT 与 IP_PKTINFO，不依赖对非本地地址 raw bind。

实机验证包括：

- ARMv7 Linux 上的 IPv4/IPv6 校验和、奇数长度、空包与端口碰撞回包。
- 多客户端、连续报文与文件描述符生命周期。
- 路由器到独立 Android peer 的真实非本地源地址回包，覆盖两种地址族。
- 每种地址族下 0、1、3、64、1200、1400、4096、32768 字节负载，共 16 组交付；包括大包分片。
- 全 LAN 接管后，经电脑 Wi-Fi 的 DNS、IPv4/IPv6 HTTPS 和 IPv4/IPv6 STUN 联网。

Windows CS2/完美平台最初的连接失败与关闭代理后恢复，构成排查线索；尚未用修改后的版本完成新的玩家进服验收。不能把 UDP 测试直接写成游戏已修好。

## 资源与回退

- 关闭核心时短测 CPU 平均约 5.4%；核心稳定但未接管时约 5.8%。
- 原始启动阶段曾出现约 99% 的总 CPU 使用。曾尝试限制 Go 并行度为 2，虽然降低了启动峰值，但后续真实订阅重载触发超时，因此撤回这一限制，保留原并行度。不能把更低的 CPU 数字单独当作性能改进。
- 未发现本次相关系统日志中的 OOM、看门狗复位、内核崩溃或 WAN 链路断开。事后正常日志不能排除未记录的瞬间异常。
- 核心停止的故障注入：看门狗 8 秒内撤掉接管，保存关闭意图，恢复桥接参数。
- 管理服务停止的故障注入：看门狗 7 秒内撤掉接管，随后恢复管理服务。
- 连续两次未确认启用的实机测试：计时器重新创建，新一次启用仍按限时自动撤销；测试后生产 120 秒脚本逐字节校验恢复。
- 本机 HTTPS 健康检查使用固定公钥 pin，避免冷启动错误时钟误判；实际错误公钥测试得到 curl 90，确认没有因跳过日期检查而接受其他公钥。

- 实机订阅页显示当前配置导入的 86 个节点；不捏造原订阅链接或更新时间。
